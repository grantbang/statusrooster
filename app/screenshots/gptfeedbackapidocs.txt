My blunt take:

It scales decently to “early real product.”
It does not yet scale like Better Stack / UptimeRobot / Pingdom.

What it’s doing well

The script has several strong choices already.

It uses async I/O with httpx, which is exactly what you want for lots of network-bound checks. It also puts a semaphore around outbound work so you do not blast the machine with unbounded sockets. That is a real scaling control, not toy code. 

checker

It also has a smart three-phase flow:

load and filter due monitors

run checks concurrently

process writes, incidents, and alerts

That separation is a good sign. It means you are already thinking in “scheduler + workers + side effects” terms instead of one giant blob. 

checker

Batch-writing checks is another good move. Writing every check one-by-one would get ugly fast. You already recognized that and added a batch path with fallback. 

checker

So this is not bad. It is actually pretty solid for where you are.

Where it will start to struggle
1. You load all monitors every run

run_checks() calls get_all_monitors(db) and then filters in Python for paused / due / interval logic. That means every cron run reads the full monitor set, even when only a subset is due. 

checker

That is fine for:

hundreds of monitors

maybe low thousands, depending on frequency and Firestore read cost

It becomes inefficient for:

many thousands

mixed intervals like 30s / 60s / 5m / 15m

lots of tenants

Why this matters for your app:
If StatusRooster grows, your scheduler should not ask “what are all monitors?” every cycle. It should ask “what monitors are due right now?”

That is one of the biggest scale issues here.

2. A new httpx.AsyncClient() is created for every request

Both check_url() and check_json_api() create a fresh AsyncClient per call. That throws away connection pooling and reuse. 

checker

 

checker

For a monitoring app, that is a significant scaling and latency problem.

Why:

more TCP/TLS handshakes

more overhead per monitor

worse throughput

more pressure on file descriptors and ephemeral ports

For real scale, you want a long-lived shared async client per worker/process with connection limits configured.

This is probably the single most important technical fix in the script.

3. The retry logic can amplify runtime badly

If a check fails, you sleep 5 seconds and retry once. 

checker

That is understandable for false-positive prevention, but operationally it means failures become expensive.

If a lot of endpoints are failing at once:

each failed monitor now occupies capacity longer

your 50 concurrency slots get stuck longer

the whole batch slows down exactly when the internet or a provider is unhealthy

That is dangerous for a monitoring platform because outages often happen in bursts.

4. Firestore writes are still very chatty

You batch check records, but you still do per-monitor update_monitor() calls, and sometimes multiple updates per monitor during the same loop. For example:

main monitor update

SSL field update

alert tracking update

incident-related changes

Those are separate DB operations in several branches. 

checker

 

checker

 

checker

That will scale worse than the network checks.

In apps like yours, people often assume “the HTTP checks are the hard part.” Usually the hidden problem becomes:

datastore read/write volume

scheduler inefficiency

alert fanout

duplicated per-monitor updates

5. Reads + writes + alerting are tightly coupled in one job

The same run is doing:

due-selection

actual checking

monitor stats mutation

check writes

incidents

alert sending

webhook delivery

That works early on, but it creates a scale and reliability coupling:
If alert delivery slows down or a webhook target hangs, your checking loop can become back-pressured.

You do await alert sends inline in the loop. 

checker

 

checker

For a real monitoring SaaS, checks and notifications should become separate pipelines.

6. SSL checks use blocking sockets via executor

For SSL and HTTPS metadata, you offload blocking socket/cert work with run_in_executor. That is acceptable, but at large scale it can become threadpool-heavy and harder to reason about. 

checker

 

checker

Not your biggest issue right now, but it is not ideal forever.

7. Uptime bars are updated by rewriting arrays on the monitor doc

The script reads daily_uptime_bars and hourly_uptime_bars, mutates Python lists, trims them, and writes the whole arrays back. 

checker

That is okay at small size, but it has drawbacks:

repeated document rewrites

possible contention if multiple workers touch same monitor

doc growth pressure

inefficient for long-term historical analytics

For your app, this is “fine for dashboard UX,” but not ideal as the core analytics storage model.

So… does it scale?
Practical answer

For MVP / early paying customers:
Yes, probably.

For hundreds to maybe a few thousand monitors total, with moderate intervals:
Probably yes, if infra is decent.

For serious multi-tenant scale:
No, not in this exact form.

The main limiting factors are:

full-table scan of monitors each run

per-check client creation

inline alerting/webhooks

too many monitor document updates

batch-oriented scheduler instead of due-job queueing

What I would change first for StatusRooster

If this were your codebase and you asked me where to spend effort, I’d do these in order.

1. Reuse a shared httpx.AsyncClient

This is the highest-ROI fix.

Keep one client per process / worker with connection pool limits. That alone will improve throughput and reduce overhead a lot.

2. Stop scanning all monitors every cycle

Move to a “due_at” model.

Instead of:

read all monitors

filter in Python

Do:

query monitors due before now

claim them

run checks

write next_due_at

That is the scheduler model you want.

3. Separate checking from notifications

The checker should produce events:

monitor.down

monitor.up

ssl.expiring

keyword.failed

Then hand those off to a queue/background worker for email, Slack, and webhooks.

That makes the checker fast and predictable.

4. Consolidate monitor updates

Build one final update payload per monitor and write once when possible.

Right now the code can update the same monitor multiple times in one cycle.

5. Move historical analytics out of the monitor doc

Keep the dashboard bars if you want, but long term:

checks go to a dedicated checks store/table/collection

aggregates are computed separately

monitor doc stays small and hot

6. Think in shards/workers, not one global cron sweep

At real scale, you usually want:

scheduler decides due work

workers process partitions/shards

notification workers fan out alerts

incident logic runs idempotently

That is how you avoid one giant checker becoming the whole company.

One more subtle concern

Your retry strategy is useful, but right now it is naive in a way that can distort load. If a whole provider has issues, lots of failed checks retry five seconds later in a synchronized burst. 

checker

That can create mini retry storms.

For a monitoring app, jitter/backoff or confirmation from a second worker/region is usually better than “same worker sleeps 5 seconds and tries again.”

Bottom line

This is good SaaS-builder code.
It is not embarrassing. It is not naive junk. It shows good instincts:

async

bounded concurrency

batching

incident model

false-positive prevention

But for real scale, the architecture needs to shift from:

“one cron job loops all monitors and does everything”

to:

“scheduler queues due checks, pooled workers run them, separate pipelines handle writes and alerts.”

That is the jump from solid MVP to serious monitoring platform.
